# 本試験形式モード — 設計メモ

Refs #529 / #101 / #492

**状態: 設計方針の決定(2026-11-06 の相談)。実装は、令和8年度の公式問題を確認し、出題形式を研究してから行う。**
公式の問題・正解番号は、例年、合格発表(11月下旬〜12月上旬)に公開される。

## 1. 背景と仮説

令和8年度の本試験を受けた利用者の実感:

- 肢を1つずつ判定するなら、わりと分かる。4肢を比べて選ぶと、分からなくなる。
- 本試験の問いの言い回しに慣れていない。

仮説は「知識の不足」ではなく「**形式への慣れの不足**」。現状のアプリは、肢を1つずつ判定して理由を選ぶ形で、4肢を比較して選ぶ練習をしていない。

## 2. 位置づけ(決定)

**本試験形式を主役にし、2段階で全肢決着に進む。**

```text
① 本試験形式で1問を出す(問い文 + 4肢。4択から選ぶ)
   ↓
② 肢ごとに、判定 → 誤り箇所タップ → 理由選択(既存の全肢決着)
   ↓
③ 結果(肢ごとの採点 + 「本試験なら正解/不正解」)
```

- #101(ミニ模試)の「全肢に理由をつけて決着、の核を薄めない」は、②が残ることで満たす
- 対象は `zenshi`(全肢判定)のみ。`calc` / `spot` は今のまま

## 3. 出題形式

第一版は次の3形式。問題データの `choices`(○×)から、画面側の変換で作る(本試験の問いの言い回しは、公式問題の研究後に決める)。

| 形式 | 問いの例 | ①の選択 | ②への入り方 |
|---|---|---|---|
| 単一選択 | 正しい(誤っている)ものはどれか | 肢を1つ選ぶ | 選んだ肢と残りの肢から、4肢の ○× が決まる。その判定を②の第1段階へ流し込む |
| 組合せ | 正しい(誤っている)ものの組合せはどれか | 組合せを1つ選ぶ | 選んだ組合せから、4肢の ○× が決まる。その判定を②の第1段階へ流し込む |
| 個数 | 正しいものはいくつあるか | 個数を選ぶ | 個数だけでは、どの肢が○か決まらない。②は肢ごとの判定から普通に始め、選んだ個数との矛盾は結果画面で示す |

### 変換の方針

- 変換は、画面に依存しない純粋な関数(例: `lib/exam-format.ts`)にし、テストを書く
- 組合せの選択肢は、4肢から作れる6通りのうち、正解を含む4つを選ぶ。並びは問題IDなどで固定する
- 個数の答えは○の数から導く。問題データに個数用の項目は足さない
- 問題ファイルの形(`types/`)は、変換のために変えない

## 4. ○の数の偏りと、既存問題の直し方

### 現状(`69c569d` 時点の計測。#529 より)

全127問のうち、全肢判定(zenshi)は119問(すべて4肢)。

| ○の数 | 問題数 |
|---|---|
| 1つ | 4問 |
| 2つ | 112問 |
| 3つ | 3問 |

○が2つに偏っており、個数問題にすると答えがほぼ「二つ」になる。単一選択も、出せる問題がほとんどない。

### 方針

- 既存問題の肢を1つ反転し(×肢を正しい内容に直して○にする。逆も同じ)、○の数を散らす
- **目標の配分**(仮置き。本試験の傾向を研究したあとで調整する):
  ○1つ 約2割 / ○2つ 約4割 / ○3つ 約2.5割 / ○4つ 約1割
- 組合せ形式は、もともと○が2つの問題が向いている。直す必要があるのは、単一選択と個数に使う問題
- 直す量は約60問。一度にはやらず、次の順で進める
  1. **新規の問題**は、設計時に○の数を決めて作る
  2. **既存の問題**は、論点ごとの拡充や照合のついでに、少しずつ直す

### 精度担保(省略しない)

肢を反転すると、法的な中身が変わる。

- 直した問題は `verified: false` に戻す
- 照合シート(`docs/verification/*.md`)を更新する
- 人が原文で確認できたら `verified: true` にする
- `CLAUDE.md` の「法的文言は、照合で誤りが見つかったときだけ直す」には、この件の例外として、変更の理由と範囲を追記する(実装時)

## 5. 成績

利用者が1人で、履歴を捨ててよいため、データの移行は考えない。

### 肢ごとの採点は残す

判定 → 誤り箇所 → 理由 の肢単位の採点と、配点(○肢2点 / ×肢3点)は、**本試験の研究が済むまで動かさない**。弱点判定・召喚状・成長グラフは、これに依存している。

### 本試験形式の正誤を別の軸として足す

`Attempt` に、次の項目を足す(型の変更。実装時に確認する)。

- 問題の形式(単一選択 / 組合せ / 個数)
- 選んだ答え
- 本試験として正解だったか

1問ごとに、次の2つが記録される。

- 本試験形式で正解できたか
- 全肢で決着をつけられたか(理由まで言えたか)

#529 の仮説を、この2軸で直接確かめる。

- 全肢決着はできるのに、本試験形式で外す → **形式への慣れ不足**
- どちらも外す → **知識不足**

ダッシュボードに「本試験形式の正解率」と「全肢決着率」を並べて出す。

### 勘の扱い

- 本試験形式の正解そのものには、**得点を付けない**。勘で当てても点が伸びない、というこのアプリの核を保つ
- 習熟(`perfect`)の判定と、SRSの間隔を伸ばす条件は、**本試験形式で正解し、かつ全肢決着も正解**のときだけにする

### リセット

- 保存のキーを新しくするか、バージョンを上げて、旧データを読まない
- バックアップのインポートは、古い形式の控えを、壊れずにはっきり断る
- リセットの前に、今の成績をエクスポートしておくことを勧める(使い捨てでよければ不要)

## 6. 既決事項との関係

| 既決事項 | この設計での扱い |
|---|---|
| `Attempt` を全件履歴で保存 | 守る。項目を足す。今の履歴は、利用者の判断でリセットする |
| 弱点判定=最新結果 / SRS=最終挑戦日 / 成長グラフ=全履歴 | 守る。習熟の条件に、本試験形式の正解を加える(5章) |
| 3段階スコアリング・満点46点(○肢2点 / ×肢3点) | 当面は動かさない。研究後に判断する |
| 問題形式は3種(`zenshi` / `calc` / `spot`) | 変えない。本試験形式は、`zenshi` の出し方の違い |
| #101: 判定のみの簡易採点にしない | 守る。②で全肢決着に進む |

`Attempt` の型の変更と、習熟の条件の変更は、既決事項に触れるため、**実装前に提案・確認する**。

## 7. 進め方

1. この設計メモを置き、#529 に決定を記録する
2. 令和8年度の公式問題の公開後、次を研究して `docs/` に記録する(問題文は丸写ししない)
   - 問いの言い回しと、形式ごとの出題比率
   - 1問の長さと構成(事例の有無、組合せの並べ方)
   - 論点の分布(#492 と同じ素材で進める)
3. 研究をもとに、次を決める
   - 問いの定型文
   - ○の数の配分の目標
   - 配点を動かすかどうか
4. 実装を、次の順で別イシューに切り出す
   1. 変換関数(`lib/exam-format.ts`)とテスト
   2. `Attempt` の型変更と、保存のリセット
   3. 画面(①と、②への接続、結果画面)
   4. 出題の入口(通常との切替、ミニ模試との接続)
   5. ダッシュボードの2軸表示
5. 並行して、新規問題は○の数を決めて作り、既存問題は少しずつ直す(4章)
