# 本試験形式モード — 設計メモ

Refs #529 / #101 / #492

**状態: 設計方針の決定(2026-11-06 の相談)。実装は、令和8年度の公式問題を確認し、出題形式を研究してから行う。**
公式の問題・正解番号は、例年、合格発表(11月下旬〜12月上旬)に公開される。

## 1. 背景と仮説

令和8年度の本試験を受けた利用者の実感:

- 肢を1つずつ判定するなら、わりと分かる。4肢を比べて選ぶと、分からなくなる。
- 本試験の問いの言い回しに慣れていない。

仮説は「知識の不足」ではなく「**形式への慣れの不足**」。現状のアプリは、肢を1つずつ判定して理由を選ぶ形で、4肢を比較して選ぶ練習をしていない。

## 2. 位置づけ(決定)

**本試験形式を主役にし、2段階で全肢決着に進む。**

```text
① 本試験形式で1問を出す(問い文 + 4肢。4択から選ぶ)
   ↓
② 肢ごとに、判定 → 誤り箇所タップ → 理由選択(既存の全肢決着)
   ※ ①の正誤は明かさず、①の答えから②の判定を決めない。各肢を独立して判定する
   ↓
③ 結果(肢ごとの採点 + 「本試験なら正解/不正解」+ ①の答えと②の判定が食い違っていないか)
```

**②は①と独立して記録する。** ①の答えから4肢の○×を決めて②の第1段階へ流し込むと、①を外した問題には必ず肢の判定ミスが含まれ、既存のエンジンは判定ミスを0点で終える。その結果「本試験形式は不正解だが、全肢決着は正解」というケースが観測できなくなり、形式への慣れ不足と知識不足を見分ける、という目的を果たせない。①の答えは保持し、②では正誤を先に明かさず、各肢を独立して判定する。

**①の正誤は、②の全肢の判定が終わるまで見せない。** 既存の `ZenshiEngine` は、各肢の判定の直後に、その肢の正誤を表示する。そのままだと、単一選択で①に選んだ肢を②で判定した時点で①の正誤が分かり、残りの肢の判定にも影響する。そこで、本試験形式では、②で**4肢の判定(○×)を先に集め、全部の判定が終わるまで正誤を表示しない**。そのあとの誤り箇所・理由の段階では、肢ごとの正誤を示してよい(判定は記録済みのため)。通常の出題の挙動は変えない。

- #101(ミニ模試)の「全肢に理由をつけて決着、の核を薄めない」は、②が残ることで満たす
- 対象は `zenshi`(全肢判定)のみ。`calc` / `spot` は今のまま

## 3. 出題形式

第一版は次の3形式。問題データの `choices`(○×)から、画面側の変換で作る(本試験の問いの言い回しは、公式問題の研究後に決める)。

| 形式 | 問いの例 | ①の選択 | ②への入り方 |
|---|---|---|---|
| 単一選択 | 正しい(誤っている)ものはどれか | 肢を1つ選ぶ | ②は肢ごとの判定から始める(①の答えから判定を決めない)。結果画面で、①の答えとの食い違いを示す |
| 組合せ | 正しい(誤っている)ものの組合せはどれか | 組合せを1つ選ぶ | 同上 |
| 個数 | 正しいものはいくつあるか | 個数を選ぶ | 同上。選んだ個数と、②で付けた○の数の食い違いを、結果画面で示す |

3形式とも、②への入り方は同じ(独立した判定)。①の答えは、②の採点には使わず、「本試験形式の正誤」の記録にだけ使う。

### 形式の適用条件

使える形式は、問題の○の数で決まる(○が0つの問題は対象外)。

| ○の数 | 単一選択 | 組合せ | 個数 |
|---|---|---|---|
| 1つ | 可(「正しいものはどれか」) | 不可 | 可 |
| 2つ | 不可(正解が2つになる) | 可(「正しいもの」または「誤っているもの」の組合せ) | 可 |
| 3つ | 可(「誤っているものはどれか」) | 不可 | 可 |
| 4つ | 不可 | 不可 | 可 |

- 組合せは、○が2つの問題だけ。正しい肢も誤った肢も2つなので、問いの向きによらず正解が1つに決まる。○が1つ・3つ・4つでは、2肢の組合せで正解を表せない
- 単一選択は、○が1つなら「正しいもの」、3つなら「誤っているもの」。○が2つ・4つでは、正解が1つに決まらない
- 個数は、○が1〜4つのどれでも使える(「なし」は第一版では使わない)
- **適合しない形式は出さない。** ○が4つの問題は、個数でしか出せない(4章で、○4つを約1割にとどめている理由)
- 出題時は、問題の○の数に合う形式の中から選ぶ。選び方(ランダムか、弱い形式を優先か)は、研究後に決める

### 変換の方針

- 変換は、画面に依存しない純粋な関数(例: `lib/exam-format.ts`)にし、テストを書く
- 組合せの選択肢は、○が2つの問題について、4肢から作れる6通りのうち、正解を含む4つを選ぶ。並びは問題IDなどで固定する
- 個数の答えは○の数から導く。問題データに個数用の項目は足さない
- 問題ファイルの形(`types/`)は、変換のために変えない

## 4. ○の数の偏りと、既存問題の直し方

### 現状(`69c569d` 時点の計測。#529 より)

全127問のうち、全肢判定(zenshi)は119問(すべて4肢)。

| ○の数 | 問題数 |
|---|---|
| 1つ | 4問 |
| 2つ | 112問 |
| 3つ | 3問 |

○が2つに偏っており、個数問題にすると答えがほぼ「二つ」になる。単一選択も、出せる問題がほとんどない。

### 方針

- 既存問題の肢を反転し(×肢を正しい内容に直して○にする。逆も同じ)、○の数を散らす。**1つの肢の反転で動く○の数は、±1だけ。** ○が2つの問題は、1肢の反転で、○1つか○3つになる。**○4つにするには、○2つの問題の×肢を2つとも○に直す(2肢の反転)** 必要がある。現状は、○3つの問題が3問しかなく、○4つの問題が0問なので、○4つの目標は、2肢の反転(または、新規問題)でしか満たせない
- **目標の配分**(仮置き。本試験の傾向を研究したあとで調整する):
  ○1つ 約2割 / ○2つ 約4.5割 / ○3つ 約2.5割 / ○4つ 約1割(合計100%)
- 組合せ形式は、もともと○が2つの問題が向いている。直す必要があるのは、単一選択と個数に使う問題
- **直す量の見積り**(全肢判定119問に、目標の配分を当てはめた場合): ○1つ 約24問(現状4)/ ○2つ 約54問(現状112)/ ○3つ 約30問(現状3)/ ○4つ 約12問(現状0)。○2つの問題のうち約59問を直す。内訳は、○1つにする約20問(1肢ずつ)、○3つにする約27問(1肢ずつ)、○4つにする約12問(2肢ずつ)。のべ約70肢の反転。新規問題が、これらの配分を満たす分だけ、直す量は減る
- 反転は、1肢でも法的な中身を書き直す作業(次の「精度担保」)なので、量が多い。目標の配分は仮置きで、研究後に調整する。**○4つの問題は、個数形式でしか出せない**(3章)ので、○4つの目標を下げて、直す量を減らす選択肢もある
- 一度にはやらず、次の順で進める
  1. **新規の問題**は、設計時に○の数を決めて作る
  2. **既存の問題**は、論点ごとの拡充や照合のついでに、少しずつ直す
- **直したあとは、旧い履歴を使わない。** 利用者の成績をリセットするのは1回だけで、その後に回答した問題の肢を同じ問題IDのまま反転すると、変更前の `Attempt` が、変更後の肢の結果として扱われる(たとえば、変更前に満点だった記録で、未挑戦の内容が満点扱いになり、復習が後回しになる)。さらに、成績は利用者の端末(localStorage)にあるため、問題を直すPRから端末の履歴を消すことはできない。直す前に作った控え(バックアップ)を復元すると、直す前の履歴が戻ってくる。そこで、次の運用にする(利用者が1人で、昔の成績は残さなくてよいため)。
  - **昔の成績は全部リセットする**(5章。2026-11-06 に利用者が決定)
  - リセットのあとに肢を直した問題は、**履歴を消すのではなく、読むときに無視する。時刻ではなく、問題の版番号で判別する**
    - 問題の側に、内容の版番号(例: `revision`。肢を直すたびに1つ上げる。未指定は1)を持たせる
    - 回答のとき、**画面が実際に表示した問題データの版番号**を、肢の `Attempt` と問題単位の記録に記録する(例: `questionRevision`)
    - 成績の集計(弱点判定・SRS・成長グラフ・習熟)は、記録の版番号が、現在の問題データの版番号と一致するものだけを使う。一致しない記録は、履歴として残すが、集計に使わない。控えを復元したあとの集計も同じ
    - 直す前の控えを復元しても、版が合わない記録は、集計に使われない
  - **時刻(直した日時と `answeredAt` の比較)は使わない。** `answeredAt` は端末の時刻(`app/play/page.tsx`)なので、端末の時計が進んでいると、直す前の記録が新しく見える。さらに、PWA の Service Worker は、オフライン時に、キャッシュした古いページを返す(`public/sw.js`)ので、直した日時のあとにも、直す前の問題に回答できてしまう。回答時に表示した問題の版を記録すれば、どちらの場合も判別できる
  - 旧い履歴は残る(集計に使わないだけ)ので、全件履歴を保つ既決事項は守る。`Attempt` と `Question` の型の変更を伴うため、実装前に確認する
  - **既存問題の肢を直す作業は、この仕組みができてから始める**(7章)

### 精度担保(省略しない)

肢を反転すると、法的な中身が変わる。

- 直した問題は `verified: false` に戻す
- **`source.level` と `source.answerLevel` も、再照合まで `unverified` に戻す。** `verified` を戻しても、`source` は別の記録なので、直す前の `primary` が残り、未照合の肢の根拠が実態より強く見えてしまう
- **`lawVersion` も、直した肢の条文について当て直す。** 版と基準日の関係を確認できるまでは、`driftChecked` を `unchecked` に戻す
- 照合シート(`docs/verification/*.md`)を更新する
- 人が原文で確認できたら `verified: true` にする
- `CLAUDE.md` の「法的文言は、照合で誤りが見つかったときだけ直す」には、この件の例外として、変更の理由と範囲を追記する(実装時)

## 5. 成績

利用者が1人で、履歴を捨ててよいため、データの移行は考えない。

### 肢ごとの採点は残す

判定 → 誤り箇所 → 理由 の肢単位の採点と、配点(○肢2点 / ×肢3点)は、**本試験の研究が済むまで動かさない**。弱点判定・召喚状・成長グラフは、これに依存している。

### 本試験形式の正誤を別の軸として足す

`Attempt` は肢単位の記録で、肢ごとに独立して保存される。ここへ「形式・選んだ答え・本試験として正解か」を足すと、1問の本試験形式の回答が4件の肢の記録に重複し、どの記録が同じ1問の挑戦かを確実に判別できない(中断や一部の保存失敗のときに特に)。ダッシュボードで「本試験形式の正解率」と「全肢決着」を問題ごとに突き合わせられなくなる。

そこで、**問題単位の記録を別の型として持つ**(型の変更。実装前に確認する)。

- 新しい型(例: `QuestionAttempt`)に、挑戦ごとの一意なID、`questionId`、問題の形式(単一選択 / 組合せ / 個数)、選んだ答え、本試験として正解だったか、回答時の問題の版番号(`questionRevision`)、`answeredAt` を持たせる
- 肢ごとの `Attempt` には、同じ挑戦を指す共通のID(例: `questionAttemptId`)を足し、問題単位の記録と結べるようにする
- 中断などで肢の記録が一部しかない挑戦は、「全肢決着」の集計から除く(扱いは実装時に決める)
- **控え(バックアップ)は、肢ごとの `Attempt` と問題単位の記録の両方を保存・復元する。** 現行の控えと `StorageAdapter` は `Attempt` だけを扱うので、両方を扱うよう広げる。復元のときの検証は、次のとおり。**正当な記録は、1件も落とさない**
  - 形式が不正な記録(型の不一致、IDの重複など)がある控えは、現行の控えと同じく、インポート全体を断る
  - 共通のID(`questionAttemptId`)を持たない肢の `Attempt` は、正当な記録として、そのまま取り込む。通常の出題・`calc`・`spot` の回答と、本試験形式でない回答が、これに当たる
  - 問題単位の記録だけがあって、肢の記録がない挑戦(①のあとで中断した場合)も、正当な記録として取り込む。「全肢決着」の集計には含めない
  - 共通のIDを持つ肢の記録に対応する問題単位の記録がない場合(保存失敗など)も、肢の `Attempt` は取り込む。2軸の集計には含めない
  - 現在の問題データにない問題ID・肢の記録は、拒否しない。読み込み側で無視する(問題データの入れ替え前に書き出した控えとの互換性を保つため。お気に入りの控えと同じ扱い)
- 控えを復元したあとの集計にも、4章の「版番号が一致する記録だけを使う」を適用する

1問ごとに、次の2つが記録される。

- 本試験形式で正解できたか
- 全肢で決着をつけられたか(理由まで言えたか)

#529 の仮説を、この2軸で直接確かめる。

- 全肢決着はできるのに、本試験形式で外す → **形式への慣れ不足**
- どちらも外す → **知識不足**

ダッシュボードに「本試験形式の正解率」と「全肢決着率」を並べて出す。

### 勘の扱い

- 本試験形式の正解そのものには、**得点を付けない**。勘で当てても点が伸びない、というこのアプリの核を保つ
- 習熟(`perfect`)の判定と、SRSの間隔を伸ばす条件は、**本試験形式の回答については**、本試験形式で正解し、かつ全肢決着も正解のときだけにする
- **通常の出題・`calc`・`spot` の回答は、これまでの条件(満点)のまま**とし、本試験形式の正解を求めない(本試験形式の正解が存在しないため。求めると、通常の出題の習熟が進まなくなる)。問題の習熟は、その問題の最新の回答で判定する。最新が本試験形式の回答なら前者、それ以外なら後者の条件を使う

### リセット

- 保存のキーを新しくするか、バージョンを上げて、旧データを読まない
- バックアップのインポートは、古い形式の控えを、壊れずにはっきり断る
- リセットの前に、今の成績をエクスポートしておくことを勧める(使い捨てでよければ不要)

## 6. 既決事項との関係

| 既決事項 | この設計での扱い |
|---|---|
| `Attempt` を全件履歴で保存 | 守る。共通のIDを足し、問題単位の記録を別の型で持つ(5章)。今の履歴は、利用者の判断でリセットする |
| 弱点判定=最新結果 / SRS=最終挑戦日 / 成長グラフ=全履歴 | 守る。習熟の条件に、本試験形式の正解を加える(5章) |
| 3段階スコアリング・満点46点(○肢2点 / ×肢3点) | 当面は動かさない。研究後に判断する |
| 問題形式は3種(`zenshi` / `calc` / `spot`) | 変えない。本試験形式は、`zenshi` の出し方の違い |
| #101: 判定のみの簡易採点にしない | 守る。②で全肢決着に進む |

`Attempt` の型の変更(共通IDの追加と、問題単位の新しい型)、`Question` の型の変更(`revision`)、`Attempt` への `questionRevision` の追加、習熟の条件の変更は、既決事項に触れるため、**実装前に提案・確認する**。

## 7. 進め方

1. この設計メモを置き、#529 に決定を記録する
2. 令和8年度の公式問題の公開後、次を研究して `docs/` に記録する(問題文は丸写ししない)
   - 問いの言い回しと、形式ごとの出題比率
   - 1問の長さと構成(事例の有無、組合せの並べ方)
   - 論点の分布(#492 と同じ素材で進める)
3. 研究をもとに、次を決める
   - 問いの定型文
   - ○の数の配分の目標
   - 配点を動かすかどうか
4. 実装を、次の順で別イシューに切り出す
   1. 変換関数(`lib/exam-format.ts`)とテスト
   2. `Attempt` への共通IDの追加、問題単位の新しい型、問題の版番号(`revision` / `questionRevision`)による旧い履歴の無視、保存のリセット、控えの保存・復元(両方の記録)
   3. 画面(①と、②への接続、結果画面)
   4. 出題の入口(通常との切替、ミニ模試との接続)
   5. ダッシュボードの2軸表示
5. **新規問題**は、実装と並行して、○の数を決めて作る(4章)
6. **既存問題の肢を直す作業**は、4章の「問題の版番号を記録し、版が合わない履歴を無視する」仕組みと、保存のリセットができてから始める。そのあとは、論点ごとの拡充や照合のついでに、少しずつ直す
